## What M6 is (as built)
`captureEvidenceSnapshot(store, request)` (service) → `buildCaptureSnapshot` (pure) → `canonical.ts` (order/instant canonicalization) → frozen `createEvidenceSnapshot`. Flow: gate `admitted` → validate `fixtureId`/`capturedAt` → provider integrity (`verifyProviderArchiveRecord` **iff supplied**) → normalize anchor → **full-stream idempotency pre-check** (`capturedAt==anchor && capturedBy=="evidence_capture"` anywhere in the stream → `already_exists` before any sequence is minted) → `sequence = head.sequence+1`, `previousSnapshotId = head.id` → build (M5 derive → sort markets/signals, canonicalize availability/odds, normalize nested instants → mint) → `appendSnapshot` → map outcomes. Identity `= evidenceSnapshotId(fixtureId, capturedAt, sequence)` **excludes** `modelVersion`; `contentHash` **includes** it. `SNAPSHOT_MODEL_VERSION="23B.daily-evidence.v1"`, `CAPTURE_ENGINE="evidence_capture"` (hardcoded, not env). Diagnostics are ephemeral (returned, never in the hashed body).

**Objective assessment:** M6's construction/identity/hash/idempotency/fail-closed logic is correct and well-tested. There is **one closure-level scope gap** (MC-1: the §4.7/DoD-5 mandatory `evidence_capture` odds record is not written or required by the capture service), one non-fail-closed throw (MC-4), and several activation/sustained/recovery items — most **inherited from the frozen Sprint-23 evidence store**, which M6 may not modify (§0/§5.1) and which is materially LESS hardened than the M2/M3 adapters (no append mutex; silently skips malformed lines).

## Findings

Each finding: **id · failure condition · current behavior · user/data impact · detectability · recoverability · closure class · owner · control.**

### A. Input / admission
Green (fail-closed, tested): `not_admitted`; invalid `fixtureId`/`capturedAt` → `invalid_input`; provider integrity failure → `invalid_input`; M5 no-valid/omission-only derivation (empty markets, unsupported canonical market, no scored markets) → `derivation_failed` with **nothing written**; malformed market element → `derivation_failed`. Archive read failure → `archive_error` (never swallowed).

- **MC-1** · §4.7/DoD-5 **mandatory `evidence_capture` odds record is neither written nor required** · `captureEvidenceSnapshot` takes only an `EvidenceArchiveStore`; it writes no odds record and does not verify one exists. `odds.ts::bestOddsSnapshotFromOddsRecord` only *projects* an optional M3 record into `bestOddsSnapshot`; it is not invoked by the service. · a "created" capture can exist with **zero** odds records — a *failed capture* per DoD-5 · detectable (structural: no odds store in the signature) · recoverable (wire the coupled odds write) · **class A (must fix / confirm before closure)** — the M6 plan line explicitly scopes §4.7 to M6 and DoD-5 is a binary gate; **confirm whether the coupled odds-record write is M6-scoped or deferred to M9 wiring**. When wired, note the two-write (snapshot + odds) has no transaction (MC-2/MC-5 apply). · owner **M6 (confirm) / M9** · control: capture must, per event, also admit exactly one `evidence_capture` odds record keyed by `captureId`, and treat zero-odds as a failed capture.
- **MC-7** · retained provider/odds **input reference is optional and unverified at mint** · `providerRecord?` is integrity-checked only when supplied; never required; no provider/odds record id is stored in the snapshot body (linkage is coordinate-derivable: `(fixtureId, capturedAt)→captureWindowKey→(source,fixtureId,captureWindowKey)`) · a snapshot can be minted whose retained replay basis is not verified to exist → future replay may find nothing · detectable at replay, not at mint · recoverable if the input was in fact admitted (M4) · **class C (activation)** — does **not** violate a frozen clause now (§2.E is M2/M4's persistence duty; linkage identity is M7's) · owner **M7** · control: at activation, require+verify the retained provider input (and the §4.7 odds record) for `(source, fixtureId, captureWindowKey)` before/at mint.

### B. Canonicalization
Green (tested/verified): array-order independence (`sortSupportedMarkets` by `(marketKey,selectionKey)`, `sortSignals` by `key`, codepoint `cmp` not `localeCompare`); duplicate market `key::selection` and duplicate signal `key` → frozen minter rejects → `invalid_input`; unstable object-key order → `canonicalizeEvidence` sorts keys → hash-stable; NaN/Infinity/negative/out-of-range numeric fields → frozen minter validates → `invalid_input`; unknown market keys cannot reach mint (M5 emits only canonical §2.B pairings); comparator ties on equal keys are the duplicate case (rejected).

- **MC-4** · **malformed `operatorAvailability`** (`restrictedCountries`/`operatorKeys` null/non-array) · `canonicalizeOperatorAvailability` spreads `[...oa.restrictedCountries]` (and the frozen minter reads `operatorKeys.length`) with **no array guard** → **throws out of `captureEvidenceSnapshot`** (the sole non-fail-closed path; markets/signals come from M5 and are safe) · an uncaught throw instead of a categorized `invalid_input` — one bad optional field aborts the call · detectable (throw) · recoverable (guard) · **class C (activation)** — caller-preventable; the type declares arrays, so only a runtime type-violation triggers it; dormant · owner **M6** · control: array-guard the two lists in `canonicalizeOperatorAvailability` (return `invalid_input`), mirroring the M5-MM-1 fix.
- *(note)* case/Unicode: keys are ASCII canonical (`§2.B`, `season_<market>_<venue>`); free-form string fields (`operatorKey`, `competitionId`, `source`) are **not** NFC-normalized by `canonicalizeEvidence` — composed↔decomposed variants would hash differently (inherited M2/M3 concern; upstream normalization duty). Not an M6 defect.

### C. Version
Green: missing `modelVersion` → defaults to `SNAPSHOT_MODEL_VERSION`; no env dependence (hardcoded → no "stale environment model version"); a `modelVersion` bump re-capturing an existing window is short-circuited by the full-stream pre-check → `already_exists` (returns the original, never conflicts); rollback re-capturing an existing window → `already_exists` (history untouched).

- **MC-3** · **different M5 constants under the same `modelVersion` string** (mixed-version deploy / silent constant edit) · `modelVersion` is a hardcoded string **not bound to a fingerprint of the M5/shared constants**; identity excludes `modelVersion` · two deployments compute the **same id, different `contentHash`** for one capture → serial: 2nd → `immutable_violation` (fail-closed); concurrent on the no-mutex file store: **both may persist → conflicting rows under one identity** · detectable (`immutable_violation`, or `verifyEvidenceChain` sequence_duplicate) · recoverable (single-writer + version discipline) · **class C (activation)** (structural fix is D) · owner **M6/M9** · control: enforce §4.4 — bump `modelVersion` on ANY constant change; ideally derive/verify the version from a constants fingerprint so a stale string cannot mask changed constants.

### D. Identity / hash
Green (tested): same content → duplicate no-op; different content, same id → `immutable_violation`, **never overwritten** (test); id excludes `modelVersion`, hash includes it (test); M6 normalizes the anchor and nested instants (`resolvedAt`, `bestOdds.capturedAt`) so equivalent timestamps yield an identical hash (addendum A7); oversized snapshot bounded by frozen caps (`MAX_EVIDENCE_SIGNALS=64` / markets 32 / operatorKeys 64) → `invalid_input`, not OOM.

- **MC-8** · **shared `canonicalizeEvidence`/sha256** serializer or hash-primitive change (or a Node-major `JSON.stringify` shift) · all historical evidence `contentHash`es fail recomputation at once (§4.9-G, register R2) · integrity checks (`verifyEvidenceChain`) fail archive-wide; **note the frozen evidence store does NOT verify hashes on read** (unlike M3), so reads still return rows — hash stability governs *replay/integrity*, not store availability · detectable (verifyEvidenceChain) · **class D (sustained/Postgres)** · owner **M7** · control: freeze `canonicalizeEvidence`+sha256 under change control; any successor algorithm dispatches from an external write-epoch registry — **no in-body `hashAlgoVersion`/new field** (Constraint 6).

### E. Persistence (frozen `EvidenceArchiveStore` — M6 may not modify it, §0/§5.1)
Green: archive unavailable / insert throw / connection reset / transaction abort → `archive_error` (surfaced, test); no read-after-write dependency (returns the built/append record); memory adapter is atomic within a process.

- **MC-2** · **no single-writer serialization** · the frozen evidence **file adapter has NO in-process append mutex** (unlike the hardened M2/M3 adapters — its header still warns "concurrent appenders can interleave admission checks and both write"), and `captureEvidenceSnapshot` does a lock-free read-modify-write (pre-check → latest → build → append) · concurrent/multi-process/host captures of one fixture can both pass the pre-check + sequence derivation and both append → **duplicate rows** (same id+hash) or, with drifted content, **conflicting rows** (same id, different hash) — the file store does **not** cross-check ids on read (unlike M3), so a conflict persists silently, surfaced only by `verifyEvidenceChain` (sequence_duplicate). **No multi-process/host safety is claimed.** · **divergent physical history** for the in-flight capture (never a mutation of prior rows) · detectable only by a `verifyEvidenceChain` sweep · recoverable (single-writer; quarantine) · **class C (activation)** — already required by addendum A3 · owner **M6/M9** · control: external single-writer (advisory lock / single cron); the Postgres cutover with `UNIQUE(id)` + app-level hash-conflict raise closes it structurally (D-side).
- **MC-6** · **corrupt/torn existing row is silently skipped** · the frozen store's `readNdjson` skips unparseable lines and returns `[]` on any read error (fail-**open**, unlike M3's fail-closed) · a corrupt line vanishes from `listSnapshots`/`latestSnapshot` → the pre-check may miss an existing same-window snapshot and **re-mint**, or derive a wrong sequence → duplicate/gap · low-visibility corruption; **not** an M6 mutation · detectable only by `verifyEvidenceChain` (not by the store) · recoverable (sweep + quarantine + restore) · **class E (recovery/runbook)** · owner **M9/ops** · control: scheduled `verifyEvidenceChain` sweep with alerting; line-level quarantine/restore; Postgres isolates per-row.
- **MC-5** · **no fsync / no durability barrier** · the file adapter's `appendFile` resolves before an OS flush; `captureEvidenceSnapshot` returns `"created"` on that resolve · under power-loss a reported-`created` row can be lost, or a torn tail left (→ MC-6) — **no crash durability is claimed** · a success may briefly precede durability · detectable (post-crash sweep) · recoverable (idempotent re-run: the pre-check re-mints a lost row, or returns `already_exists` for a survivor) · **class E (recovery/runbook)** · owner **M9/ops** · control: back up before activation; post-crash integrity sweep + idempotent re-run; Postgres commit is the durability barrier at migration.
- **MC-10** · **immutable_violation + pre-check make a window's snapshot permanent** · once a window has any `evidence_capture` snapshot, the pre-check returns `already_exists` for every re-capture, and a different-content same-id append is `immutable_violation` · a **bad** snapshot (e.g. from a since-fixed derivation bug) is permanent for its window — cannot be overwritten or corrected in place · detectable (re-derivation vs stored) · recoverable only forward · **class E (recovery/runbook)** · owner **M7/M9** · control: correct via a **new `modelVersion` + a new capture window** (never overwrite, §4.9/§5.4); investigate via deterministic re-derivation from retained inputs (diagnostics are ephemeral but reproducible).

### F. Process
Green: crash before persistence → nothing written, retry re-mints (deterministic id); crash after commit before response → retry → pre-check `already_exists` (idempotent at-least-once); process restart → stateless service; cancellation mid-append → torn tail handled as MC-6; oversized snapshot bounded (frozen caps). Deploy-overlap / mixed-version → MC-2 + MC-3.

### G. Downstream / replay (assessed, not implemented — M7 obligations)
- **canonical order reconstructable:** the stored body is already canonically ordered (M6 sorts + normalizes instants); replay reproduces it **iff M7 re-applies the identical M6 canonicalization** (`sortSupportedMarkets`/`sortSignals`/`normalizeInstant`, codepoint `cmp`). Control: M7 reuses the exact M6 canonicalization.
- **historical constants / modelVersion registry:** M6 hardcodes one constant set + version and has **no registry**; §4.9-R3/R4 require the full `modelVersion→{M5 model constants + shared frozen thresholds `EVIDENCE_MIN_SAMPLE_SIZE`/qualification thresholds}` mapping be retained permanently (MC-9, below). Owner M7.
- **source references / byte-faithful body:** replay resolves inputs by coordinates (source-string stability = M2 concern); byte-faithful reproduction depends on MC-8 (serializer) + retained-input fidelity (M2/M3) + M7 canonicalization reuse.
- **diagnostics for investigation not persisted:** correct (frozen body has no such fields); investigation is via deterministic re-derivation — **recoverable, not lost**, provided retained inputs + version-pinned code are available (M7).
- **MC-9** · **no `modelVersion→constants` registry; shared thresholds are part of the frozen derivation set** · `class D (sustained)` · owner **M7** · control: version-pinned retention of every modelVersion's complete constant set (model + shared thresholds); read-compat for every emitted `schemaVersion`/`modelVersion`; never re-key/rewrite rows.

## Explicit answers
1. **Can any failure corrupt or overwrite historical snapshots?** **No overwrite/mutation** — append-only; `decideSnapshotAppend` never rewrites; `immutable_violation` rejects different-hash same-id; the pre-check returns the existing row. The only "corruption" is external disk damage, which the frozen store *silently skips on read* (MC-6) — a pre-existing row becoming unreadable, **not** M6 mutating history.
2. **Can any failure return success without a durable snapshot?** **Yes, narrowly** — the file adapter has no fsync (MC-5): `"created"` is returned on `appendFile`-resolve, which is not a durability barrier, so a power-loss can lose a reported-created row. Recovery is idempotent re-run. (An ambiguous Postgres commit returns `archive_error`, not success.)
3. **Can any retry create divergent history?** **No under the required single writer** (retry hits the pre-check `already_exists` or id+hash `duplicate`). **Yes if single-writer is not enforced** — the frozen file store has no mutex (MC-2), so a concurrent retry/second worker can append a duplicate or conflicting row.
4. **Can a mixed-version deployment mint conflicting content under one identity?** **Yes** — identity excludes `modelVersion`; different constants (or version strings) yield the same id, different hash (MC-3). Serial → `immutable_violation` (fail-closed); concurrent on the no-mutex store → both may persist (conflicting rows). Mitigated by single-writer + version discipline.
5. **Is rollback immutable-safe?** **Yes** — append-only + the full-stream pre-check mean a rolled-back deploy re-capturing an existing window returns `already_exists` (history untouched). New windows mint under rolled-back code; historical rows are never mutated. (Caveat: rolling back constants under an unchanged `modelVersion` string is the MC-3 discipline issue for *new* windows only.)
6. **Is an uncertain Postgres commit recoverable through idempotent retry?** **Yes** — the deterministic id `(fixtureId, capturedAt, sequence)` + content hash + full-stream pre-check make re-capture idempotent, **provided** the Postgres adapter enforces `UNIQUE(id)` + app-level same-id/different-hash → `immutable_violation` and single-writer/DB uniqueness (D-gate). The file adapter alone (no uniqueness/mutex) can double-write under concurrency.
7. **Which M6 values become frozen at first production mint?** `SNAPSHOT_MODEL_VERSION="23B.daily-evidence.v1"`; `CAPTURE_ENGINE="evidence_capture"`; the `evidenceSnapshotId` formula `(fixtureId, capturedAt, sequence)`; the full `contentHash` body basis (incl. `modelVersion`, `schemaVersion="23.0.0"`, `capturedBy`, `evidenceScore`, `qualification`, canonically-sorted `supportedMarkets`/`signals`, canonicalized `operatorAvailability`/`bestOddsSnapshot`, `competitionId`/`seasonId`, `sequence`, `previousSnapshotId`); `canonicalizeEvidence`+sha256; the M6 canonicalization rules (market/signal sort keys, codepoint `cmp`, `normalizeInstant`); the M5 model constants **and** the shared frozen thresholds that produce `evidenceScore`/`qualification`; the signal `key`/`source` string formats; the window-anchor `capturedAt` derivation.
8. **What must M7 preserve permanently?** The complete `modelVersion→{model constants + shared thresholds}` mapping for every version ever minted (§4.9-R3); the historical-input identity linkage (snapshot coordinates → provider/odds archive records) so replay resolves retained inputs; `canonicalizeEvidence`/sha256 semantics (or an external write-epoch registry — no in-body version field); the M6 canonicalization code to byte-reproduce bodies; source-string stability; read-compat for every emitted `schemaVersion`/`modelVersion`; and the absolute rule to never rewrite or re-key archived rows.
